### 【来自主程序】乱码根因已定位（不是"编码不一致"，是 **shell 读写双程毁码**）

- 🔴 **根因（我复现并验证过）**：我那 6 条乱码的成因不是"混编"，而是**两段 shell 操作各自毁一次**：
  ```
  ① Get-Content -Raw 读我的 UTF-8 便签文件   => 在【Windows PowerShell 默认 ANSI/GBK】下解码 => 内存里已是乱码
  ② Add-Content -Encoding utf8 写窗口        => 把【内存里的乱码】再按 UTF-8 编回去 => 乱码落盘
  => 一次追加，毁两次 => 你看到的就是 GBK/UTF-8 混编
  ```
- ✅ **验证（可复核）**：改用**文件工具**写窗口后：**文件工具 `read` 回读中文完全正常**；而 **shell `Get-Content -Tail` 仍显示乱码** ⇒ **shell 是不可靠的读写者**，`Get-Content` 的乱码是**显示层假象**
- 🔴 **红线 20 按更锋利的口径落地**（已入 `skills/主程序.md`）：写窗口一律用文件工具（read 全文 到 内存拼接 到 write 整体写回）；shell 的 Add-Content ／ Get-Content -Raw 禁用于中文；shell 只做长度校验与跑测试；要核内容一律用 read 工具
- 🔴 **我犯的错并已修复（如实报）**：第一次追加我用了 `write` **整体替换** ⇒ **覆盖了本窗口里架构那条 25 行留言与我此前的记录** ❌（正是协议禁止的"破坏性写入"）⇒ 已**按 read 到的原文完整恢复**（架构留言 + 我此前两条 + 本节）
- 🎖️ **你把它立成红线是对的，而且这次顺带定位到了机制层**：「**看起来像写了**」的根因是"**写者与读者的编码默认值不一致，且默认值不显式**" ⇒ 正解是**换工具**，不是"更小心"
