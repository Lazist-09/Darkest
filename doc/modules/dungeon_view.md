## 1. DD 的机制（wiki 原文要点）

| # | 事实 | 对我们的意义 |
|---|---|---|
| **①** | **「A dungeon consists of rooms connected by corridors, as seen in the dungeon map in the lower right hand corner of the screen.」** | 🔴 **地图在右下角**（= `ui_spec §11.1` 已定 ✅） |
| **②** | **Rooms** = 大灰方块；**Corridors** = 深灰小格，**1~8 格**连接两房间 | **"格"是基本单位**（不是"房间"） |
| **③** | 🔴 **「traversing each tile counts as a single round」** | 🔴 **走一格 = 一回合** ⇒ 状态效果与光照计**按格计** ✅ |
| **④** | 🔴 **走廊格可含**：**战斗**（交叉剑）· **Curio**（开箱）· **障碍**（墙）· **陷阱**（蛛网）· **隐藏房**（金星）· **饥饿**（隐藏） | 🔴 **这些内容【先以图标显示在地图上】** |
| **⑤** | 🔴 **走到那格才触发** | 🔴 **那就是"无缝"的核心**：**先看到、走到才发生** ✅ |
| **⑥** | **未探索 = 暗**；**已侦察 = 暗但轮廓更亮**；**已走过 = 浅灰** | 与我们的 `HasVisited` 一致（扩展为三态） |
| **⑦** | **往回走 ⇒ 士气损失** | 与我们有"重访代价"一致 ✅ |
| **⑧** | **重进已走过的走廊 ⇒ 小概率生成新战斗/饥饿/陷阱**；**光越暗概率越高**（≤50 ⇒ +2.5%；=0 ⇒ +5%） | 🔴 **那是"清完还得走"的代价来源** |

## 2. 🔴🔴 核心裁定：**我们缺的是【行走视图】这一层**

```
DD 有【两层视图】：
   ① 【行走视图】—— 走廊/房间的**画面**（队伍在左、横向；走到哪看到哪）
   ② 【右下角小地图】—— 图标**先告诉你**格子里有什么
❌ 我们只有 ②（点房间 = 直接"传送"）⇒ 🔴【没有"行走"这个状态】
⇒ 🔴 **所以"不无缝"的根源不是"场景切换"，而是【缺少"行走"这一层】**
```

### 2.1 ✅ 裁定：**合并为一个场景 + 一个状态机**

```
🆕 **`DungeonScene`（唯一场景）** + 状态机：
   Walking   ← 【行走视图】：可前进 / 后退 / 看地图 / 看背包
     ├─ 走到【战斗格】⇒ Encounter
     │     Encounter  ⇒ 敌人【从右侧进入画面】（背景/队伍/地图【不重建】）
     │     → Battle     ⇒ 战斗 HUD 展开（**同一个场景**）✅
     │     → Resolved   ⇒ 敌人消失 ⇒ 回 Walking ✅
     ├─ 走到【Curio 格】⇒ Curio 交互（物件出现在行走视图里 ⇒ 三按钮）✅
     ├─ 走到【障碍/陷阱】⇒ 就地处理
     └─ 走到【房间】⇒ Room 视图（房间画面）+ 房间内容（Curio / 战斗 / 空）
```

🔴 **铁律**：**状态切换时【背景 / 队伍 / 右下角地图】不得重建**
⇒ 那是"无缝"的**可测定义**（见 §4）✅

## 3. 🔴 术语与"格"的模型（定的东西）

```
🔴 **基本单位 = 【格】**（tile）
   · 一【格】= 一个可站立的点；**走一格 = 一回合**（DD 原文③）✅
   · **房间** = 格的【汇合点】（可达 4 向邻接）· **走廊** = 连接两房间的格序列（1~8 格）
   · 🔴 **所以"段数"这个概念应被"格数"取代**（`m7_6_verification` 的 V2 要改口径）⚠️
```

🔴 **每格有【内容】**（数据驱动 ⇒ `battlefield.json`/`dungeon_tiles.json`）：

| 字段 | 含义 |
|---|---|
| `kind` | `empty` / `battle` / `curio` / `obstacle` / `trap` / `secret` / `hunger` / `room` |
| `payload` | 引用 id（`curio_id` / `encounter_id` / …）**不得内联定义**（P26 的同一纪律） |
| `revealed` | **三态**：`unexplored`（暗）/ `scouted`（暗+亮轮廓）/ `visited`（浅灰） |

## §0.1 🔴 用户裁定（`#362`）：**地牢层一进来【不该是战斗】，移动到房间才触发**

> 🔴 **用户原话**：「**地牢层不该一进来就是战斗，需要在移动到房间才会触发**」

### ✅ 两条裁定

```
🔴 **① 进地牢的第一个相位 = `Walking`**（**不是 `Battle`**）——
   即：**进地牢 ⇒ 行走模式** ⇒ **玩家自己走** ⇒ **走到房间才触发** ✅
   ⇒ 📌 **本文 §2.1 的状态机【早就规定了这一点】**（`Walking` 是首个相位）⚠️
      —— 🔴 **而实现没跟上**（见下"根因"）✅

🔴 **② 触发点 = 【房间】**（**走廊不触发**）——
   ⇒ 🔴 **它【明确了】`dungeon_grid_rules_draft.md` 的"每格都可能遇敌（规则暂留）"** ⚠️
      ⇒ ✅ **即："每格"是【暂留】的；而现在确定的触发点是【房间】** ✅
   ⇒ 📌 **判据**：**走走廊格 ⇒ 不触发**；**进房间格 ⇒ 触发遭遇** ✅
```

### 🔴 根因（实测 · `BattleRoot.cs:85`）

```csharp
public override void _Ready()
{
    if (ExpeditionContext.IsActive)
        ExpeditionContext.Flow!.Session.EnterPhase(FlowPhase.Battle);   // 🔴 无条件置 Battle
    ...
    NewGame();                                                          // 🔴 无条件起一场战斗
}
```
```
🔴 **原因在【片 4】**：它**退休了 `Expedition.tscn`** ⇒ 🔴 **`Battle.tscn` 成了唯一宿主** ⚠️
   ⇒ 于是"**进地牢**" = 加载 `Battle.tscn` = **立刻 `NewGame()`** ❌
⇒ 📌 **即：【场景已合并，但状态机还没合并】** ⚠️
   —— 而那正是 **`BattleRoot.cs:89` 的注释自己预告的**：
      "**片 3 把两场景并成一个状态机后，这行会被状态机自然取代**"
   ⇒ 🔴 **所以这是【片 3（场景内切战斗 / 状态机合并）未完成】的后果** ✅
```

### ✅ 正解（**宿主 `_Ready()` 按【请求】分流**）

```
🔴 **不能"无条件 NewGame()"** —— 而应：
   ① **请求 = 出发远征**（`ConsumeRequestDungeon()`）⇒ **进 `Walking`**（**不起战斗**）✅
   ② **请求 = 冒烟/试验**（`--battle-piece3-exp` 等）⇒ **才 `NewGame()`** ✅
   ⇒ 📌 **即：`NewGame()` 从 `_Ready()` 里【挪出去】，改为【由请求或触发驱动】** ✅
⇒ 🔴 **而"触发"的路只有一条**：**进房间 ⇒ 起战斗**（那才是 §0.1 ② 的判据）✅
```
