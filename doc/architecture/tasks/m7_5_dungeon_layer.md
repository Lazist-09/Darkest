## 🔴 0. 本卡要解决的那件事（**这是它存在的唯一理由**）

> **`#256`/`#257` 的结论**：**A1 与 A2 在 M7 的机制集合下【数学上不可兼得】。**
> ```
> 完成率 = p^6；落 [40,70] 需 p ≈ 0.90 ⇒ 需 10% 场次"输"
> 而"输"的代价是死人/濒死 ⇒ 正撞 A1 的「阵亡 ≤0.1（几乎不死人）」
> A1 余量：死门 +21% · 阵亡 +11% ⇒ 不够把 p 从 0.983 压到 0.90
> ```
> 🔴 **纪律 16 的推论**：**判据不可达时，缺的往往不是"数值"，而是【一个让玩家自己选择难度的机制】。**

**本卡就是那个机制**：**光照计 = 玩家自选"更危险 / 更富有"** ⇒
**难度从"数值"交回"玩家的选择"** ⇒ **完成率才会变成一个有意义的指标**（它反映玩家的风险偏好，而不是我们的调参）。

## D0 · 🔴 光照计（本卡核心）

### D0.1 数据结构

```
LightValue : int, 0~100
· 进图 = 100
· 档位（照抄 DD 五档）：
     Radiant  >75
     Dim      75 ~ 51
     Shadowy  50 ~ 26
     Dark     25 ~ 1
     Black    = 0
```

### D0.2 🔴 我们独有的映射：**柴火 = DD 的 Torch + Firewood 合一**

> **依据**（`#247`）：**我们的资源字面上就叫「柴火」**，而 DD 有**两种火**（Torch 提光 / Firewood 扎营）。
> **而且 DD 的规律是「扎营可免费回满光照」** ⇒ **合并天然**。

| 行为 | 效果 | 消耗 |
|---|---|---|
| **前进一个节点** | **光照 −15** | 无 |
| **手动提亮** | **光照 +30** | 🔴 **1 柴火** |
| 🔴 **扎营** | **光照回满 100** + 扎营两阶段 | **1 柴火**（已有） |
| **事件节点** | 可选「举火把前进」(+20) / 「摸黑前进」(−20，但见 §D0.3 收益) | 无 / 无 |

```
起手 100；6 个节点 ×(−15) = −90
⇒ 不管它 → 末段落到 ~10（Dark）
⇒ 玩家要选：柴火用来【扎营（回满 + 恢复）】还是一次次【提亮】
⇒ 🔴 而柴火只有 2 份 ⇒ 【真取舍】✅
```

### D0.3 🔴 收益端：**我们的"战利品"= 补给掉落**（无金钱也能成立）

> 🔴 **这是本卡最关键的设计判断**：DD 的"越暗越富"给的是**战利品（换钱）**，
> 而**我们无金钱** ⇒ 若照抄"掉战利品"，**收益端是空的**，光照计就退化成"纯粹的难度滑块" ❌。
> ✅ **解法：把收益换成【补给本身】** ⇒ **越暗 → 越危险 + 越多补给** ⇒ **风险/收益闭环成立，且零新增系统**。

| 档位 | 战斗掉落额外补给 | 事件节点额外补给 |
|---|---|---|
| **Radiant** | 无 | 无 |
| **Dim** | **1 份** | **1 份** |
| **Shadowy** | **2 份** | **2 份** |
| **Dark** | **3 份** | **3 份** |
| **Black** | **4 份** | **4 份** |

> 🔴 **v1.11 改（`#270`）—— 从"概率制"改为"按档确定给份数"**：
> **实测（150 趟）额外补给掉落仅 0.48 份/趟，而柴火消耗 2.69/趟** ⇒ **摸黑换不回补给** ⇒
> **"越暗越富"没兑现**，玩家自然不走 Dark/Black（**那是理性选择**）。
> ✅ **改为按档确定给份数** ⇒ 期望 ≈ **3.4 份/趟**（提升 ~7 倍）。
> 🔴 **为什么去掉掷骰**：**"自选风险"必须让玩家算得出** ——
> 赌博式掉落会让"摸黑"变成**运气**而非**决策**（同 `#240` 否决"事件可跳过"的原则）。
> ⚠️ **旧写法（25%/50%/75%/95% 概率 ×1 份）已作废**；`P21 ④` 的"按档单调不减"**仍适用**。

> **补给种类**：柴火 / 口粮 / **支援包**（三者皆可掉）。
> ✅ **闭环**：越暗 → 危险 ↑ + 补给 ↑ → 玩家可"**摸黑搏补给**" ⇒ **风险/收益成为玩家的选择** ✅

### D0.6 🔴 两个定义与论证（v1.00 补，**勿删**）

#### (1) 🔴 "摸黑"的精确定义

```
❌ 不能用"中途经过 Shadowy"：
   起手 100，每节点 −15 → 100→85→70→55→40→25→10
   ⇒ 玩家【什么都不做】也会在第 4 个节点进 Shadowy
   ⇒ "中途经过"几乎每个 run 都满足 ⇒ 【没有区分度】

✅ 正确定义：摸黑 run ＝【结束时光照 ≤ 50】（Shadowy 及以下）
   · 一次不提亮      → 结束 ~10（Dark）  ⇒ 摸黑 ✅
   · 提亮 2 次 (+60) → 结束 ~70（Dim）   ⇒ 不算 ✅
   · 扎营 2 次(回满) → 结束 ~70（Dim）   ⇒ 不算 ✅
   ⇒ 它反映的是"玩家【有没有花柴火提亮】" ✅
```

#### (2) 🔴 「提亮」为什么**不是被"扎营回满"支配的选项**

> **看起来**：「提亮 +30」花 1 柴火，而「扎营」同样 1 柴火却**回满 100** ⇒ 提亮被支配 ❌
> **实际上不是**：

| | 扎营 | 提亮 |
|---|---|---|
| 光照 | 回满 100 ✅ | 只 +30 ⚠️ |
| **风险** | 🔴 **33% 夜袭** | ✅ **无风险** |
| 次数 | 受柴火数限制（起手 2） | 同样受柴火数限制 |

⇒ **「提亮」= "花 1 柴火买 +30 且不冒险"** ⇒ ✅ **它有独立价值**（应急 + 规避夜袭）。
📌 **登记此论证，防止以后被当成"垃圾选项"删掉。**

## D1 · 侦察（Scouting）

### 规格

```
进节点前掷骰：
   基础侦察概率 = 25%
   + 光照加成（Radiant +15% ⇒ 40% ； Dim +7.5% ⇒ 32.5%）
侦察成功 → 🔴【提前显示下一个节点的类型】（普通战 / 精英战 / 事件）
```

> 🔴 **设计意图**：**让"选路"从"二选一赌"变成"基于信息的规划"** ——
> **这是我们"位置驱动 / 精密操作"定位在地牢层的自然延伸**（`#247`）。

### 验收

| 用例 | 期望 |
|---|---|
| 概率 | 大样本下基础 25%（+光照加成），且写 `RngDraw` |
| 成功 | 下一节点类型**可见**；**失败则不可见** |
| 🔴 **只揭示"下一个"** | **不得揭示更远**（只揭示下一节点类型）—— 🔴 **设计理由**：侦察的价值是"让选路**基于信息**"，**不是"预知全程"**；预知全程会让选路退化成"照着最优解走"，**决策就消失了** ❌<br>⇒ **建议做成执行级断言** |
| 🔴 **不改节点序列** | 侦察**只揭示信息**，**不改变节点内容** ✅ |
| **失败时字段** | `ScoutResultEvent.success == false` ⇒ **`revealedNodeType` 应为 `null`**（避免"失败却也带类型"的歧义） |
| UI | 侦察结果**与"未知"有明确区分**（见 `ui_spec.md` §2 必显 **13**）—— 不能让人误以为已侦察 |

### 规格（`#248` 已定）

```
背包格子 = 【12】
· 柴火    1 格 / 个
· 口粮    1 格 / 个          ← 🔴【不堆叠】（这是"取舍"的来源）
· 支援包  1 格 / 个

```

#### 🔴 「整备」环节（v1.05 补，`#264` —— 原规格缺口）

> 🔴 **原规格缺口**：上面写了"默认想装 15 格 > 12 ⇒ 必须取舍"，**但没写"谁在什么时候砍那 3 格"** ❌
> ⇒ 若不定，实现方只能自己编 ⇒ 又会出现"**规格缺口 → 实现偏差**"（`#244` 的教训）。

```
【远征前 · 整备】
· 列表式界面（**不必新美术**）；玩家在 **12 格内自由配置**
· 给一份【推荐配置】作默认：
       🔴 柴火 2 ／ 口粮 9 ／ 支援箱（support_crate）1     （= 12 格满）
· 🔴【局内不可改】—— 否则"出发前决策"就没有分量
```

##### 🔴🔴 命名裁定：`support_crate`（支援箱）≠ `support_pack`（支援包）（v1.06，`#265`）

> ⚠️ **触发原因**：主程序 D2 窗口把推荐配置写成"**支援包 1**"，而第 9 行又把 `while_carried` 载体叫
> **`CarriesSupportCrate`** —— **两个名字指向的可能是同一个东西，但我在 §D2 定义了【两个不同的物品】** ❌
> ⇒ **必须按 `[纪律 15：并列项同层检查]` 的同类问题处理：命名冲突会导致实现把两件东西合成一件。**

| 物品 | id | 作用 | 必需性 |
|---|---|---|---|
| 🔴 **支援箱** | **`support_crate`** | **在背包里时【每回合 +1 SP】**（`while_carried` duration） | 🔴 **必需** —— **不带 ⇒ SP 完全不恢复 ⇒ 支援位直接废掉** |
| **支援包** | `support_pack` | **一次性：消耗 1 个 → 立即 +2 SP** | 可选（消耗品） |

🔴 **两条硬要求**：

1. **推荐配置必须带 `support_crate`（支援箱），而不是 `support_pack`** ——
   否则**默认配置下 SP 完全不恢复**，成为一个**玩家看不见的陷阱**（与 `#248`"不带 SP 物品 → UI 必须提示"同源）。
2. **新增加载级校验**：`tuning.inventory.recommended_loadout` **必须包含 `support_crate`** ——
   缺它即**启动报错**（治"默认配置踩陷阱"）。
3. **命名必须在数据与事件里区分**：`support_crate`（载体/装备，`while_carried`）× `support_pack`（消耗品）
   —— **不得都叫"支援X"**（同类教训：`#253` 三个抗性并列、`#247` `(b)/(c)` 同名异义）。

#### 🔴 背包满时的处理（v1.05 补，`#264`）

> 🔴 **原写法"包满 → 自动丢弃"会削弱"摸黑"的动机**：

```
"越暗越富"的收益若因【包满】拿不到 ⇒ 玩家摸黑的动机被削掉 ❌
⇒ 光照计的核心闭环就漏了（只有风险、没有收益）
```

✅ **裁定**：**包满时不自动丢，而是【弹出"丢弃哪一格"的选择】**（或允许**就地消耗口粮腾格**）
—— **让"摸黑搏到的补给"真的能拿回来**。

🔴 **取舍来自"装不下"**：

```
默认想装：柴火 2 + 口粮 12 + SP 恢复物品 1 = 【15 格】 > 12
⇒ 必须取舍：
   · 少带口粮 → 吃得差（Starve/半饱）→ 单趟累积更陡
   · 少带柴火 → 扎营/提亮更少 → 光照更暗（危险 ↑ 但补给 ↑）
   · 不带 SP 恢复物品 → 🔴【支援位不恢复 SP】（见下）
```

#### 🔴 SP 的恢复改为【背包物品的 buff】（`#248`）

```
背包里有一个物品（**占 1 格**）
· 它在背包里时 → 每回合 +1 SP（由【该物品的 buff】提供）
· 不带它       → 🔴 SP【完全不恢复】
· 起手默认带 1 个
```

> 🔴 **数值零改动**：`#213` 的 `regen 1 / cap 4 / cost_skill 2 / cost_reinforce 2` **全部不变**，
> **只把"恢复"的提供者从引擎改成物品**。
> ✅ **它同时满足三件事**：保留节奏约束（`#211` 精髓）· SP 有物质来源 · 可取舍。
> ⚠️ **必须配套 UI**：**不带该物品时明确提示"支援位不会恢复 SP"** —— 否则这不是决策，是**陷阱**。

### 🆕 支援包（一次性）

```
消耗 1 个 → 立即 +2 SP
来源：事件节点 / 战斗掉落（越暗越多，见 §D0.3）
```

### 验收

| 用例 | 期望 |
|---|---|
| 格子上限 | **≤12**；超出**不可携带**（UI 明确提示"背包已满"） |
| 起手默认装不下 | 默认配置（柴火 2 + 口粮 12 + SP 物品 1）**必然超格** ⇒ 强制取舍 ✅ |
| 不带 SP 物品 | 🔴 **SP 完全不恢复**，且 UI **明确提示** |
| 带 SP 物品 | 每回合 **+1 SP**（与 `#213` 的 regen 值一致） |
| 支援包 | 消耗 → **+2 SP**，且**封顶 cap 4** |
| 掉落入包 | 额外补给**先入包**；包满 → **丢弃**（需 UI 提示） |

## D3 · Pass / 待命 → 受士气伤害

### 规格

```
【待命】（`#213`/S5.2 已引入）：
· 消耗 0 SP · 该单位本回合不再行动
· 🔴 新增：【待命】使该单位 **−5 士气**（照抄 DD 的 Pass base 5）
```

> 🔴 **理由**（与 `#240` 否决"事件可跳过"同一逻辑）：**"待命"是免费行为** ⇒
> **免费 = 没有代价 = 不是决策** ⇒ **必须给它一个代价**。
> ⚠️ **但要注意与 SP 的交互**：若"没 SP 只能待命"是常态，那这条会变成**二次惩罚** ⇒
> **验收：待命次数占支援位回合数的比例 ≤ 某阈值**（否则说明 SP 太紧，该调 SP 而非加罚）。

### 验收

| 用例 | 期望 |
|---|---|
| 待命 | 该单位 **−5 士气**；写入 `TurnSkippedEvent(Reason: passed, MoraleDelta: -5)` |
| 🔴 **必须有一条会待命的策略**（v1.11 补，`#270`） | 实测 **150 趟里待命 0 次**（本驱动策略从不 Pass）⇒ **㉗ 无样本 ⇒ V8 无法判红** ❌<br>✅ **要求：加一条保守策略**（**`SP < 2` 且无可用技能 → Pass`**）并报它的待命比例。<br>🔴 **但更值得注意的是**："策略从不 Pass"本身说明**支援位总有不耗 SP 的事可做** ⇒ **`#213` 的"待命"机制从未被需要** ⇒ "待命 −5 士气"**从未生效** ⇒ **登记为待查**（若加了保守策略仍 ≈0 ⇒ 该机制可能是多余的） |

### D5.4 🔴🔴 完成率区间【怎么重推】—— v1.12 补（`#271`）

> 🔴 **本条规定"方法"，不是"数值"** —— 因为 `#270` 只写了"**等 M7.5 全落定后再定区间**"，
> **而"等"不是方法**（判据悬空 ⇒ 下一轮又会变成"调数值"，正是**纪律 16** 要防的）。

#### ① 先问：`[40,70]` 是怎么来的？

```
M7 时代它是【拍】的：依据是"3 场皆胜 48% ⇒ 要有难度"
⇒ 🔴 而 #256/#257 已证明：【那时玩家没有选择】——
   完成率 90% 不是"玩家打得好"，而是"没有别的路可走"
⇒ 所以再拍一个新的区间，会重复同一个错误 ❌
```

#### ② 🔴 正确做法：**用【玩家的行为分布】来定，而不是拍一个数**

```
报【三种策略】的完成率（其余口径完全一致）：
   ① 保守策略：多选【事件】、早扎营、维持高光照
   🔴 v1.14 修订（`#273`）：保守档【必须重新定义】—— 旧"全事件"在加了战斗目标后【必然失败（0 战斗）】，
      不再是一个"策略" ⇒ 新定义 = 【恰好达标：3 战 + 3 事件】+ 不摸黑；均衡 = 4~5 战；激进 = 全战斗 + 摸黑
      ⇒ 三档【都吃战斗损耗】⇒ V10 才真正反映【风险偏好】✅
   ② 均衡策略：默认
   ③ 激进策略：多选【战斗】、摸黑搏补给

🔴 判读（这才是 M7.5 的真正判据）：
   · 若三者【拉得开】（如 75% / 55% / 30%）
     ⇒ ✅ 设计成功 —— 玩家的选择【真的改变结果】
     ⇒ 区间取【激进档之上、保守档之下】的中带（[40,70] 大概率仍合适）
   · 若三者【挤在一起】（如 60% / 58% / 57%）
     ⇒ 🔴【设计失败】—— 玩家的选择【不影响结果】⇒ 光照计没起作用
     ⇒ 此时【不该调区间】，而该调【收益端 / 难度端】让三者分开
```

#### 🔴 ③ 为什么这条比"定一个区间"重要

```
若三种策略结果一样 ⇒ 【"完成率"这个指标不反映任何选择】
⇒ 那区间定多少都毫无意义（它只是在描述一个常数）
⇒ 🔴 所以 M7.5 的判据不是"完成率落 [40,70]"，
     而是【三种策略的完成率是否分开】—— 分开才说明"难度成了玩家的选择"
```

> 📌 **这条同时给 `#270` 的"暂不判 A2"一个明确的出口**：
> **不是"等"，而是"跑三种策略、看它们是否分开"。**

#### 判据（原 V1~V9 的其余项）

| 项 | 判据 |
|---|---|
| **侦察有效** | 侦察成功率与光照档的**相关性成立**；有 run 因侦察**避开了精英战** |
