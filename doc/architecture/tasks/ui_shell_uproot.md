```
🔴 **两种形态必须分清**（草案把两者混成一条路线）：
   **形态 A（常驻 HUD + Overlay；ScreenLayer 仍是"当前场景"）**
      ⇒ `UIRoot` = **autoload 外壳**，只提供 BaseLayer（常显 HUD）+ OverlayLayer（弹窗/转场）
      ⇒ ⚠️ **场景切换仍然发生**，只是**常驻部分不重建** ⇒ 改动面小、可分期、不动 `main_scene`

      ⇒ ScreenLayer 承载主菜单/城池/战斗 ⇒ **"场景"退化为"panel"**
🔴 **架构裁定：先做【形态 A】；【形态 B 暂缓，须先解决一处与既有裁定的冲突】**：
   · **用户 2026-09-15 裁定**（`blueprint §9.17`）：**"战斗场景是唯一宿主，地牢是它的地图模式"**
     ⇒ 🔴 **而 S4「战斗面板化」把战斗从"场景"降为"panel"** ⇒ **两条裁定直接冲突** ⚠️
   · ⇒ 🔴 **必须由策划/用户明确**：**(i) 保留"战斗 = 唯一场景"（则 S4 不做）** ／ **(ii) 改裁定为"UIRoot 是唯一外壳，战斗也是 panel"**
     ⇒ **架构不擅自改用户裁定**（红线 23②：判据/裁定不得为方便而改）✓
   ⇒ ✅ **批准范围**：**S1 收窄为【只建 shell 骨架（Base/Overlay）+ autoload 注册】**；
     **S2~S4 暂缓**（等形态决定）✓
   ⇒ 📌 **判据一句话**：**"哪些屏之间需要共享常驻状态？"** —— 只有 HUD ⇒ **形态 A 够**；要跨屏共享大量 UI 状态 ⇒ 才需 B ✓
```

## §4 🔴 裁定三：两处**接口/纪律修正**（我作为架构要改的）

```
🔴 **① `SetBaseHud(bool)` 改成【声明式】**：
   现形态 = **由调用方（panel）在每处记得声明"要不要 base hud"** ⇒ ⚠️ **那正是"靠记得"**（我们刚立的元准则：
   **动作型 > 禁止型**）⇒ ✅ **正解**：**panel 声明"我需要哪些 base hud 组件"（或由 shell 按 panel 类型查表）**，
   **默认由 shell 决定** ⇒ **新 panel 忘了声明 ⇒ 走默认，而不是"没有 HUD"** ✓
   📌 判据：**"新加一个 panel 时，需要有人【记得】做某件事吗？"** —— 需要 ⇒ **接口形状不对** ✓

🔴 **② 层级必须写清（否则又一处"两处真值"）**：
   ```
   UIRoot（外壳：Base/Screen/Overlay）
     └─ 当前 Screen = 某个 panel（主菜单 / 城池 / 唯一场景）
          └─ 唯一场景内部：DungeonView 模式状态机（Battle ⇄ Map ⇄ Curio/Camp）   ← blueprint §9.17
   ```
   ⇒ 🔴 **判据**：**"换 ScreenLayer 的 panel" 与 "场景内切模式" 是【两个层级】的切换** ——
     ⚠️ **不得混用同一个 API**（否则"谁在管当前显示"会出现两处真值，`#325` D6 家族）✓
   ⇒ ✅ 并要求：**`ShowPanel` 只切换 Screen 层；`DungeonView` 的模式切换【不经 `UIRoot`】** ✓
```
