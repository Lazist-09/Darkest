## §2 🔴🔴 架构必提：**"每格 −30"不是平移，是【量级变更】**（P30 附注 · 最高优先）

```
旧：`move.new_area = −30`，语义 = "每【段】"，1 段 ≈ 一次房间→房间推进（一趟 6~8 段）
新（瓷砖网格）：**"格" = 每个瓷砖格**（DD 走廊 1~8 格 + 房间成块）⇒ **一张图的格数远多于 6~8** ⚠️
⇒ 照字面"平移成每格 −30" ⇒ 🔴 **光照几步就到底 ⇒ 总消耗放大数倍 ⇒ 静默改难度**
⇒ 🔴 正解（二选一，~~待定~~）：
   ① **消耗绑【区域/房间】**（格内移动不耗光/耗极小；**进入新房间/新区域才 −30**）
   ② 保留"按格"，但 `cost_light_per_tile` **按"旧每段消耗 ÷ 典型每段格数"重定标**（**需先知道典型图格数**）
⇒ 📌 **定案前：该键只登记、不取值**（与用户"规则暂留"同精神）；定案时要**过一个数（策划）**
📌 提示：`#327`③ 我预警过"段→格会让数值漂移" —— **这是同一件事的第二种形态**（上次担心格 < 段，这次是格 >> 段）
```

### ✅ §2.1 **已定（v1.55 · 主程序落 `WalkLightCost`）：走格光照 = 【余数结转】⇒ 总消耗守恒**

```
🔴 主程序**自己认了草案写错**（"1 段 = 1 格 ⇒ 平移" ❌）并落了：
   `WalkLightCost.StepCost(acc, remainingTilesInSegment)` —— **代码里不写死任何数字**
   · 进段 `acc = segmentCost`（调用方给现值 30）→ **每格扣 `floor(acc / 本段剩余格数)`** → **余数结转** → **末格扣清** ✓
   · 🔴 **禁止项（已写进类注释）**：`每格 −30`（会 ×N）· `−30/N` 字面量（造新数字 + 取整漂移）
   · 🔴 **负向**：`remainingTilesInSegment <= 0` ⇒ **抛错**（调用方状态错误，**不静默兜底**）
✅ **为什么它是最优解**（主程序理由，架构确认）：**它是我 ② 的【自归一化形态】** ——
   **不需要预先知道"典型每段格数"**（那要等一张典型图才有数），且 **逐段守恒**（总量恒 = `segmentCost × 段数`）
   ⇒ **同时满足"回合按格、光照按总量等价"**，**不必绑区域、不必等统计、现在就能落、不触 `#307`** ✓
⇒ 📌 **§2 的"二选一待定"就此收敛为【余数结转】**（上面两条候选**作废，但留痕不删** —— "被推翻的决策划线保留"）
⇒ 📌 这也印证 `#327`③ 的预警是对的，而**解法不必是"绑区域"** —— **"守恒式分配"是第三种解**（比 ① 更简单）✓

```
