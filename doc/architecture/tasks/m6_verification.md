## 0. 里程碑一句话目标

> **设计意图验证型验收**：**同时**证明「破局可行——胜出靠决策（位置 / 位移 / 士气经营 / 集火取舍）而非纯运气」与「系统真触发——士气崩 / 虚弱 / 死门 / 撤退 / 美德折磨 / 位移在实战中真正发生且影响战局」，且手感（位置决策 / 无脑最优 / 时长）人工可评（[设计] verification.md §1 #119）。

M6 是**实现方 / 测试方执行**的验收：策划（#123）只负责定义标准（verification.md 已给），不实现、不跑模拟、不手动试玩。**本任务卡即 M6 的执行清单**——逐条可测、逐条可打勾，产物全部落在 `res://tests/` 与报告文件，**不写任何业务实现**（内核结算由 T-M2~T-M5 提供）。

- **边界**：本里程碑**不做**平衡数值修改（按 README §6-5「数值不当即改」：起手值迭代只走 tuning.json 参数覆盖集 / override，不当即改文档与代码）；只产出**验收结论 + 数值调整建议**供后续迭代。
- **回归范围**：review.md 两轮评审 TOP 失败点（老虎机感 / 平衡夹拧 / 角色深度）在 T-M6-03 / T-M6-04 / T-M6-07 逐条对应验证（见各卡「风险/开放」与 §6 顺带验证表）。

## 1. 验收总口径与判据（[设计] verification.md §1 #119）

切片「通过」= 下列**三组判据全部成立**，缺一不可：

| 组 | 判据（判定式） | 归属任务卡 |
|---|---|---|
| A. 模拟跑通 | `--runs 300`（≥300 场，200~500）胜率落 **40~70%**；平均回合 <6 或 >18 触发节奏告警 | T-M6-03 |
| B. 系统真触发 | 六项 KPI 全达单场下限（士气触底≥1 / 虚弱≥1 / 死门≥3 / 撤退≥1 整场 / 美德与折磨各≥1 整场 / 位移≥2），全部自然发生 | T-M6-04 |
| C. 手感 + 无软锁 + 无溢出 | 手感 3 指标人工通过（≥5 局）；无软锁（撤退重试 / 全虚弱 / 增援卡死 / 同回合多人死亡靠齐）；士气不越界 [0,100]、HP 非负、位置不越槽 | T-M6-06 / T-M6-07 |

> **判据落点**：A、B 来自内核事件流统计（同 seed 可复现）；C 来自人工试玩 + 状态机回归用例。A/B 全绿但 C 不过 → 验收仍不通过（反对「纯数据验收」，verification §1）。

## 2. 数据与确定性前提（硬约束）

- 所有 KPI 字段从**内核事件流（CombatLog）**统计，与实机演出零耦合（blueprint §8.3/§10）：删掉表现层与 UI，headless 仍凭同一内核跑完并产出全部 M6 指标。
- 每场**一个显式 seed**（`--seed N`）；所有骰子 + 策略随机一律走注入的 `IRngProvider`，抽取带单调序号 DrawCount 写入日志（blueprint §8.1/§8.2，随机层=combat_math §9 的 9 层固定调用点）。
- 数值起手值唯一落点 = `res://data/*.json`（尤指 tuning.json 参数覆盖集）；改数值只走 `--override`，**不改代码、不改文档**（blueprint §7，README §6-5）。
- 敌人策略与实机 AI **同源**（enemy.md §5.4 固定优先级表，切片关闭 15% 随机，O-19 default off）。

## 3. 任务卡

### T-M6-01 Headless 模拟器（HeadlessDriver 直驱 BattleDirector）
- **上游**：[设计] doc/modules/verification.md §2 · doc/modules/combat_math.md §9 · doc/architecture/blueprint.md §8.3/§10 · 决策：#119, #120, #112
- **依赖**：T-M0~T-M5 全部（确定性内核 + 数据管线 + IPlayerPolicy 契约就绪）
- **产出**：
  - `res://tests/MonteCarlo/HeadlessDriver.cs`（直驱 BattleDirector，**无场景树 / 无窗口 / 无 `using Godot`**）
  - `res://tests/MonteCarlo/Report.cs`（事件日志紧凑格式 → 统计输出）
  - `res://tests/MonteCarlo/README` 或程序内 `--help`（CLI 用法说明）
- **要点**：
  1. 每场显式 `seed`，new 出独立 BattleSession 并注入 `IRngProvider`；头驱动逐命令喂给 BattleDirector，同实机同对象图同 JSON 数据（blueprint §8.3）。
  2. CLI 参数：`--seed N`（单场）、`--runs N`（批量场数）、`--override key=value[,key=value...]`（参数覆盖集注入 tuning.json，不改代码）。
  3. 事件日志采用**紧凑格式**，仅保留统计所需字段：胜率、平均回合数、各角色平均输出、死门致死数、士气分布直方图、技能使用率（verification §2「强制记录」六项 + §3 KPI 六项）。
  4. 每场把抽取 DrawCount 与命令流一并留档（供 T-M6-05 逐字节回归与回放）。
  5. 边界：单场以「我方全灭 / 敌方全灭 / 撤退成功」三种终局判胜负；超时增援（第 6 回合）与撤退（O-11）都必须走内核固定调用点，不得在 headless 侧另造随机。
  6. `--runs` 支持并行分片（每场独立 seed），缓解 300+ 场性能（blueprint §12 风险 7）。
- **完成判据（可测）**：`--runs 1 --seed 42` 输出完整紧凑日志（六项强制记录字段非空）；`--override damage_float.enabled=true` 能使同一 seed 场次结果与默认关闭不同（证明 override 生效）；无任何 `using Godot` 依赖（CI 静态检查通过）。
- **风险/开放**：O-11（撤退公式未定 → 撤退结算先落 tuning.json 可配置公式 + 默认示例，正式式拍板后回填）；O-14（士气团队事件聚合口径 → 影响士气分布直方图与「士气触底」统计，先按「实例各自结算、同动作全队事件合并一次」实现）。

### T-M6-02 玩家策略（半随机 + 基线 AI 对照）
- **上游**：[设计] doc/modules/verification.md §2 · doc/modules/enemy.md §5.4/§5.5 · doc/architecture/blueprint.md §9.10 · 决策：#119, #120, #112
- **依赖**：T-M6-01（HeadlessDriver 已就绪）；T-M3/T-M5（技能可用性、敌人 AI 表）
- **产出**：
  - `res://tests/MonteCarlo/Policies.cs`（半随机策略 + 基线 AI 策略，均实现 `IPlayerPolicy`）
- **要点**：
  1. **半随机策略**：在「合法技能 + 合法目标」内按**权重随机**选取（verification §2 玩家策略行）；权重覆盖位移 / 集火 / 鼓舞等不同动作，避免只集火单调。
  2. **基线 AI 对照**：独立实现「优先打最低血」「优先击杀支援位」两条硬规则（verification §2 基线 AI 行），用于与半随机对照胜率差，暴露是否「人数碾压而非决策取胜」（verification §2 风险 5 / enemy §5.5）。
  3. **策略随机也走同一 `IRngProvider`、固定抽取时机**（行动选择阶段先抽、结算阶段后抽，blueprint §8.1），保证整场命令流可复现。
  4. 目标选择遵循「技能只选位置不选目标」总则（skill.md / glossary §2）：合法目标 = 技能 `target` 覆盖的非空位置；「部分非空只对非空生效」由内核裁决，策略侧只选合法位置。
  5. 敌方策略不在此实现：直接复用 `EnemyAi`（enemy.md §5.4 固定优先级，与实机同源）；15% 次优先随机保持关闭（#112 / O-19）。
- **完成判据（可测）**：对 `--seed N` 同一场，Policies 产出的命令流是**确定性**的（两遍一致）；半随机策略单场指令全部通过 `ISkillUseResolver` 合法性校验（无一条非法技能/非法目标）；基线 AI 与半随机各能跑满 `--runs 300` 不抛异常。
- **风险/开放**：O-28（射手 AI 规则②③互斥、威吓箭可达性 → 影响敌方压力与士气 KPI，实现按 enemy.md §5.4 直译）；O-19（15% 随机关闭保证确定性）。

### T-M6-03 Monte Carlo 主跑（平衡验证 #120）
- **上游**：[设计] doc/modules/verification.md §2 · doc/modules/combat_math.md §7（节奏试算）/§9 · doc/modules/enemy.md §5.5 · doc/architecture/blueprint.md §7（override）· 决策：#120, #124
- **依赖**：T-M6-01、T-M6-02
- **产出**：
  - 批量运行报告：胜率 / 平均回合 / 各角色平均输出 / 死门致死数 / 士气分布直方图 / 技能使用率
  - 节奏告警记录与平衡反推建议表（不落数值改，只出建议）
- **要点**：
  1. 场数 **≥300 场**（区间 200~500，越多越稳）；默认半随机策略跑主跑，另跑一版基线 AI 对照（verification §2）。
  2. 胜率可接受区间 **40~70%**；落带即平衡成立，出带触发反推（verification §2「反推规则」）。
  3. **反推规则表**（verification §2，逐字口径）：
     | 观测 | 判定 | 调整方向（走 override，不当即改） |
     |---|---|---|
     | 胜率 < 40% | 敌方压力偏强 / 我方起手偏低 | **上调我方 / 下调敌方** |
     | 胜率 > 70% | 「绝境翻盘」#11 难触发 / 敌人偏弱 | **上调敌方压力**（增援时机 #69 / 强度 #71 优先） |
     | 平均回合 < 6 或 > 18 | 节奏偏离 8~12 目标（character.md §5.2） | **调伤害 / 血量**（敌 HP 起手值 #154：50/50/38/34） |
  4. 参数覆盖集**走 tuning.json override 注入**（`--override`），同一批跑一整组覆盖集；任何「拍死在内核代码里、脱离 tuning.json 的起手值」= 架构违规（blueprint §7）。
  5. 胜率虚高时优先查「6v4 人数碾压而非决策取胜」（verification §2 风险 5 / enemy §5.5），对照基线 AI 结果判断。
  6. 节奏异常顺带暴露「士气触底是否可能」（combat_math §5.2 调节阶梯：威吓箭 CD→恐惧低语→精神震荡加士气→单次 −12，最后才加近战小兵精神技能）。
- **完成判据（可测）**：`--runs 300` 输出胜率落在 40~70%，且无节奏告警（平均回合 ≥6 且 ≤18）；日志六项强制记录齐全；对照基线 AI 的报告一并产出；若出带，报告给出明确 override 反推建议（含方向与参数键），且**不直接改任何代码/JSON**。
- **风险/开放**：O-06（敌 HP 50/50/38/34 为可推翻起手值，按 override 迭代）；O-04（精神 −8 是否足以士气触底 → M6 前不阻塞，此处验证并给调节建议）；O-21（威吓箭 −4 vs −8 口径 → 影响士气触底频率与 KPI 校准）。

### T-M6-04 系统触发 KPI 统计（#121 · 频率达标）
- **上游**：[设计] doc/modules/verification.md §3 · doc/modules/combat_math.md §5.2/§6 · 决策：#121, #123, #117
- **依赖**：T-M6-01、T-M6-03（复用事件流统计）
- **产出**：
  - 六项 KPI 逐场统计表（单场平均 / 单场下限判定 / 整场统计项）
  - KPI 不达标时的起手值回查建议（不落数值改）
- **要点**：
  1. 从事件流统计，**单场平均**达以下下限，全部为「自然发生」非构造（verification §3 表，逐字）：
     | KPI | 单场下限 | 语义 |
     |---|---|---|
     | 士气触底（归 0 并崩溃判定） | **≥ 1 次** | 折磨/美德链路能跑 |
     | 虚弱（HP 归零→虚弱） | **≥ 1 次** | 虚弱 / 回升 / 死门前置可达 |
     | 死门判定（虚弱受伤） | **≥ 3 次** | 死门是常态压力点（6 人队下较频繁） |
     | 撤退可触发 | **≥ 1 次（整场统计）** | 止损通道存在、UI 显成功率、失败可重试（#118） |
     | 美德 / 折磨各出现 | **≥ 1 次（整场统计）** | 崩溃双向结果都可达，非单向惩罚 |
     | 位移实际使用（推/拉/交换/突进/后撤） | **≥ 2 次** | 位置是活操作维度，非装饰 |
  2. 区分「单场平均下限」与「整场统计下限」：撤退、美德/折磨按整场统计，其余按单场平均（verification §3）。
  3. 死门判定计数含折磨 −10% 修正（#123）：`存活概率 = 死门抗性 − (折磨?10:0)`（combat_math §6）。
  4. 位移计数覆盖推/拉/交换/突进/后撤全部来源（enemy 位移仅由技能触发，enemy §1）。
  5. **KPI=0 回查**：某 KPI 长期为 0 → 对应系统可能被数值/AI 压死，回查 `morale.md` / `formation.md` / `enemy.md` 起手值（verification §3 备注），并在报告中给回查建议。
- **完成判据（可测）**：`--runs 300` 报告给出六项 KPI 各自单场/整场统计与下限判定；六项全达标（每项 ≥ 下限）；计数口径与 combat_math §6/#123 一致（死门含折磨 −10% 修正可复算）。
- **风险/开放**：O-14（士气聚合口径 → 士气触底与士气分布直方图口径依赖它）；O-04（士气触底是否可达）；O-11（撤退 KPI 依赖撤退公式占位）。

  - `res://tests/DeterminismTests.cs`（确定性回放）

  2. **镜像测试**：实机战斗以「录制命令流」重放，与 headless 事件日志**逐事件比对一致**（blueprint §8.3/§10）——这是「实机与 headless 共用内核」的判据。
  3. 覆盖随机层全部 9 层（combat_math §9）：命中 / 暴击 / 附加效果 / 位移过抗性 / 死门 / 崩溃判定 / 速度浮动 / 撤退 / 折磨触发，均须在固定调用点且可复现。

### T-M6-06 无软锁与边界验收（verification §5 清单）
- **上游**：[设计] doc/modules/verification.md §5 · doc/architecture/blueprint.md §12 风险 5 · 决策：#24/#114/#115/#118
- **依赖**：T-M4（士气/生存状态机）、T-M5（增援/撤退）
- **产出**：
  - 回合状态机回归用例（软锁 + 数值边界）
- **要点**：
  1. **四类软锁回归**：撤退重试循环（失败当回合不可再试，#118）、全虚弱死循环（全员虚弱缩支援位）、增援卡死（第 6 回合填位/上增益分支）、同回合多人死亡靠齐（靠齐链不中断、虚弱者不参与前移 #24/#115）——均无软锁（verification §5）。
  2. **数值边界**：士气不越界 **[0,100]**（钳制 morale §1）；**HP 非负**（含虚弱锁 1 与死门路径，O-15 口径）；**位置不越槽**（槽位编号合法、三态不漂移、靠齐留空队尾）。
  3. 导演回合状态机为唯一推进者，事件流驱动可观测每一步（blueprint §12 风险 5 缓解）。
  4. 边界用例覆盖：撤退失败后同回合再次尝试、全虚弱后无行动源、第 6 回合满编/非满编两分支、单回合内多目标连续死亡。
- **完成判据（可测）**：四类软锁 + 数值边界用例全绿（无超时/死循环/越界断言失败）；全部状态转换走内核（无 UI/场景兜底修正）。
- **风险/开放**：O-11（撤退重试语义依赖撤退公式占位）；O-20（增援强度随机切片走默认起手值，不走随机分布 → 增援卡死用例按确定性分支覆盖）。

### T-M6-07 手感与报告（#122 · 人工 ≥5 局）

- **产出**：
  - 人工试玩报告（胜负 / 系统触发日志 / 手感评分 / 数值调整建议）
- **要点**：
  1. 人工打 **≥5 局**实机（设计者/测试者，verification §4），逐局记录胜负与关键事件。
  2. **手感 3 指标**（verification §4，逐字）：
     | 指标 | 判定标准 | 通过线 |
     |---|---|---|
     | ① 有意义的位置决策 | 每回合需考虑推/拉谁、是否换人、站位影响技能可用性，而非无脑集火 | 多数回合存在 ≥1 非显然位置抉择 |
     | ② 无单一无脑最优解 | 不同局面不同应对：集火/位移/鼓舞/撤退有真实取舍，不存在「永远先 X」 | 试玩中未出现贯穿全场的唯一最优动作 |
     | ③ 单场时长 | 节奏落在暗黑地牢式紧凑区间 | **8~15 分钟** |
  3. **附加观察**（不强制但记录，verification §4）：撤退是否真有「止损 vs 赌翻盘」意义还是纯丢士气；敌人 AI 是否**可预判**（#86）、精密操作是否成立；是否出现「老虎机感」——五层随机（命中/暴击/折磨/死门/撤退 #46）是否让玩家归因运气而非决策（呼应 review 失败点 1 / README §7）。
  4. **数值调整建议**：按 README §6-5「数值不当即改」**不当即改**；建议以 override / tuning.json 参数覆盖集形式给出，走 T-M6-03 的 Monte Carlo 迭代验证后再定（README §6-7 由实现方执行）。
  5. 手感评分 1~5 或 通过/不通过，附逐局备注；A/B 判据（模拟）通过但手感不过 → 验收仍不通过。

### 数值调整建议（M6 只验收不调数值，README §6-5：走 override / JSON 迭代）
1. **节奏 / 胜率同源问题**：我方每回合 6 次行动 vs 敌方 4 次（支援位也参与攻击权重覆盖）——先调 ① 敌方行动频率（enemy_ai 规则让后排也稳定行动 + 施法者 CD1 恐惧低语已被 AI 使用）或 ② 我方支援位策略权重下调（Policies 权重未来迭代）或 ③ 直接数值：melee_soldier HP 50→60、ranged_archer HP 38→46、caster HP 34→42（units override），并下调 warrior_cleave 1.0→0.9 / lunge 0.9→0.8 倍率（skills override）拉长战线。
2. **KPI 单场下限**：胜率回到带内后，死门≥3/场需要把"进入虚弱后再被集火"场景增多——建议在 B 区迭代后复测；同动作死亡靠齐已由内核保证（无软锁）。
3. 峰值验证命令（本机）：`dotnet test --filter Name~M6Acceptance`（300 场 ~1.5s）；修改建议的 override 可在 `HeadlessDriver.RunMany(..., tweak)` 中逐组试跑，找到带内组合后再落 data JSON（由数值迭代方执行）。
