## §1 判据怎么算"对齐"（**四档判定**，避免"像/不太像"这种模糊话）

| 判定 | 含义 | 处置 |
|---|---|---|
| ✅ **已对齐** | 我方值 = 原版值（**有证据**） | 收工；**留读数**防回归 |
| 🟡 **有意偏离** | 我方**故意**不同 ⇒ **须有裁定 + 理由** | 收工但**必须写明"为什么"**（否则后人会当 bug 修） |
| 🔴 **待对齐** | 我方不同、**且无裁定** | 排期改（**这是阶段 A 的主力**） |
| ⏸ **不可判** | 原版行为**只在引擎里**（数据说不出） | 入策划 **§5 观察清单**（**不猜**）✓ |

## §3 架构侧**已识别的两处"契约不合适阶段 A"**（附处方）

### §3.1 🔴 `SlotLayout` 把"支援位"做成**一等公民** ⇒ 改 4v4 要动 **core 契约**
```
实测：`core/contracts/SlotLayout.cs` = `{ SlotCount, CombatSlots, SupportSlots }`（**构造参数 + 校验都硬编码支援位**）
   ⇒ 后果：**"战斗 4v4" 这件纯数据对齐，却要动内核契约** ⇒ ⚠️ 与"阶段 A 尽量只改数据"的意图相反 ✓
✅ **处方（架构建议 · 待主程序落）**：**把 `SupportSlots` 降级为【通用扩展位（可为空）】**——
   · 契约形状**不变**（仍能表达 6 槽），但**语义从"支援位"改为"扩展位"**，**校验放宽**（允许空/任意合法槽号）✓
   ⇒ 📌 **收益**：**4v4 与 6 槽都能表达 ⇒ 契约在阶段 A/B 都不用再改**（**契约稳定**）✓
   🔴 **判据**：**"这次对齐会不会要改 core 契约？"** —— 会 ⇒ **先看契约是不是把某个【可选的玩法概念】写成了一等公民**（那就是本条的形态）✓
```
### §3.2 🔴 **数值冻结 `#307` 与"对齐复现"直接冲突** ⇒ 需要一条**解冻口径**
```
🔴 现象：**对齐原版 = 改数值**（HP / 伤害 / 概率权重…）⇒ 而 `#307` 是**零数值改动**（当前冻结）⚠️
   ⇒ ⚠️ **不解决 → 阶段 A 走不动**（每条偏差都卡在"不许改数值"）✓
✅ **架构建议的解冻口径（待策划确认）**：
   · 🔴 **"对齐复现"是【解冻的合法理由】**（与"我们自己调平衡"区分开）✓
   · 🔴 **但必须**：**① 逐条登记**（`dd1_conformance` 的条目号 + 原版证据）· **② 一次只改一类** ·
     **③ 前后读数对照**（A1/A2/V10 + 相关单测）· **④ 改完回到冻结** ✓
   ⇒ 📌 **判据**：**"这次改数值，是为了【对齐原版】还是为了【我们认为更好玩】？"** ——
     **前者 ⇒ 可解冻（走上表）**；**后者 ⇒ 仍冻结**（属阶段 B）✓
```
