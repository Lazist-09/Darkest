# 策划师规格手册与协作规范

> 配套 `darkest-game-designer` skill。细节来自项目协议策划师 §5.x，按主题归类。

## 1. 规格交付三件套（强制，缺一不许交）

### ① 规则（原有）
机制定义 + 数值 + 边界 + 被推翻的旧决策（**划线保留，不删**）。

### ② 验收字段表（新增·强制）
任何会产出数字的规格必须同时定义"怎么测"：

| 字段 | 定义 | 数据来源（必须点名事件） | 期望 |
|---|---|---|---|
| 阵亡/场 | Σ `DeathEvent` ÷ 场数 | `DeathEvent` | ≤0.5 |
| E（敌方对我方） | 目标 `side=player` 的 `DamageEvent` 求和 ÷ 回合数 | `DamageEvent` | 实测 |

- 🔴 数据来源必须落到具体事件名；事件不存在=事件字典缺项 → 先补事件，不得在 harness 另算一份。
- 反面教材：`E` / `待命次数` / `阵亡` 三项都吃过"复测后才发现没定义"的亏。

### ③ 双向分叉口径（新增·强制）
任何剂量决策必须同时给：

```
初值：X
分叉：> 上沿 → 改 A（幅度）；< 下沿 → 改 B（幅度）；< 更下 → 改 C
硬约束：① 每次只动一个变量 ② 不得动 <禁区> ③ 连调 N 档仍不达标 → 停手上报
```
- 🔴 目标：让下游能自主迭代 2~3 轮，不必每轮回问策划。
- 已在 #224 验证有效（"敌攻 ±1 档 + 不得动敌 HP"）。

## 2. 先取数再定量（纪律）

| 情形 | 做法 |
|---|---|
| 需定数值档位 | 优先要实测；确需估算必须标「估算」，下一轮用实测替换 |
| 文档提数值 | 🔴 必须区分「实测 D」/「估算 D」，禁只写"D"（红线13） |
| 拿到实测 | 回头检查它作废了哪些旧决策（纪律14-b） |

反面教材：`D≈24` → `D≈35`（均估算）→ 实测 **20.81**；据此降 HP 决策建立在错数上。

## 3. 工作流：三段分工 + 一个环

```
策划（定义「什么算对」）──┐
                          │  规格三件套
架构师（定义「怎么核对」）──┤  契约 / 门禁 / 差异对账
                          │
主程序（实现 + 自测）──────┴──→ 结构化报告文件 ──→ 策划裁定 ──→ 下一轮
                                      ↑
                          🔴 策划可直接读（只读查数）
```

🔴 **策划可跑「只读查数」**（不改代码、不改数据）：
```
允许：跑复测入口 / 读 reports/*.json
禁止：改 .cs / 改 data/*.json / 改 doc/architecture/*
用法：改规格前先跑一次基线 → 读报告 → 再裁定
```
理由：策划是唯一不能跑代码却要拍板数值的角色——每轮"主程序跑→翻译→策划裁定"要 4 跳且翻译会丢精度。

## 4. 协作红线详表

| 红线 | 说明 |
|---|---|
| 别同文件并行编辑 | 架构/主程序可能同时改同文件（多次 file changed 冲突）——改前重读，冲突后重试 |
| 发现者≠修复者 | 抓到别层错→登记+交接，不代笔（架构侧同理不代写策划文档） |
| 走查优先抽查 4 类 | 命中几个/补几个/隔几回合/判哪一方胜负（公式有单测兜底，这 4 类没有） |
| 并列项同层检查（纪律15） | 凡并列选项先查是否真同层：数量单位(/场 vs /回合 vs /趟)·时间单位("一场"=单场还是整趟)·设计代价(位置驱动核心须排最后/排除)。做法：①列并列项同时列"它改哪个机制/哪层" ②口径不同先统一再加表 ③代价层级不同拆主/次不写"或" ④核心定位项默认排最后/排除 |
| 判据可同时成立性预检（纪律16） | 两条判据都须数值同向才满足时先验能否同时成立：①写各自方向 ②相反→立即停下不调参，先裁定放宽哪条或换不在此轴的机制 ③同向但余量不足→算清余量(两条写成共同约束同一量)。推论：判据不可达时缺的往往不是"数值"而是"让玩家自选难度的机制" |

## 5. 三角窗口投递与当轮补投（§6.7，v1.09 #297）

```
🔴 窗口是【唯一的投递通道】⇒ 写失败【就是没送到】，不能默认"对方会从别处看到"
```

| # | 要求 |
|---|---|
| ① | 写对方窗口返回 `file changed since it was read` 类错误 ⇒ 立刻重读该窗口、当轮补写，不得留到下一轮 |
| ② | 补写必须**追加**（先读全文→拼接→整体写回）——不得为"快"而整体覆盖 |
| ③ | 当轮确实写不进去 ⇒ 明确记一条待办（不静默） |
| ④ | 不得用"我已经写过了"作依据——只有 `read` 回读能证明它在窗口里 |

立条依据：策划投递 `#296`（O-78 battle_goal 拍板）写入失败未当轮补 ⇒ 拍板在主程序窗口缺席整整一轮（正是主程序开 M7.6 片(i)所需口径）。

窗口内容格式（只写"要交代的话"，不是工作日志）：
```markdown
### 轮次：<日期> · <一句话主题>
- **我做了什么**：<≤3 行>
- 🔴 **需要你做什么**：<逐条、可执行>
- **阻塞 / 待裁定**：<有就写；无写「无」>
- **权威在哪**：<doc/ 具体文件 + 章节>
```
