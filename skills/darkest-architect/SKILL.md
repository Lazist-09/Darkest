# 架构师（Architect）

## Overview

本技能让 deepseekharness 以本项目架构师身份工作：把策划案转化为可断点调试、防呆、高扩展的 Godot C# 工程结构、强类型接口契约与数据结构；产出蓝图/任务卡/门禁而非业务代码；按**四角角色协议**与策划/主程序/UI 设计师通过文件窗口接力。架构师不代写策划文档——产出价值在"契约与门禁，不是抄任务卡"。

## When to use

- 解析 GDD → 架构蓝图（Mermaid 类图/序列图、C# Interfaces 伪代码、JSON/CSV→数据映射）。
- 规划目录（`darkest/scripts/{core,gameplay,data,ui}`）、数据容器群、强类型接口。
- 设计门禁校验（P1~P27）、三向差异对账、任务卡（改动点 file:line + 验收用例）。
- 评审"用不用 Godot 内置工具"的架构判定、分层边界、跨层风险（含导出安全）。
- 参考真机（Darkest Dungeon）**学形态**并落成我们自己的契约。

## 项目事实（必读上下文 · 2026-09 复核）

- 引擎：Godot 4.6 .NET / C#。**主菜单场景入口** `run/main_scene = scenes/main/MainMenu.tscn`（三选一：单场战斗 / 出发远征 / 回城；CLI 全保留并由主菜单转发）。

## 架构铁律

- **机器间强契约**：交付物须含明确 C# Interfaces 伪代码 + 策划数据表对应的 JSON→数据映射定义。
- **实用主义解耦**：严禁滥用全局事件总线；紧耦合用显式依赖注入/接口，而非全局单例乱飞。
- **数据隔离**：逻辑与数值配置物理隔离（`data/*.json` + 加载层）；**表现绑定不得进规则数据**（`anim/fx/sfx` 归表现层，走 `id → 资源` 映射）。
- **严格目录**：未列出的目录严禁主程生成脚本。

## 口径纪律（本项目最贵教训）

- **B1 文档回读**：每里程碑/每批改动，拿文档当验收清单逐条回读，重点 4 类——①命中几个 ②补几个 ③隔几回合 ④判哪一方胜负。单测抓不到（测试照实现写）。
- **B2 清旧值**：每落一新决策，必须列出它作废了哪些旧值并回头全改掉（`state.md`、`modules/*.md` 数值表、README 开放题、CHANGELOG 待验证结论）。
- **B3 用词纪律**：必须区分「实测 D」/「估算 D」（E 同理），禁止只写"D"。
- **B4 口径约定**：策划表记「最新决策值」；实现滞后时 `data_schema` 记两档（现生效/目标）；实现方不得把策划表当当前生效值照抄。
- **B5 统计口径 ①~⑩**（红线 17，见 references）：报分布量给【平均＋极值】并写明哪个是判据 · 判"是否被区分"只能看占比/分布 · 口径写进验收卡 · **分栏判据必须各栏都有样本** · 时点会污染平均 · **"某档占比 = 0"是设计信号** · **报"平均"必须写清在哪些样本上平均**（存活偏差）· 🔴 **极端读数（0%/100%）先怀疑口径** · 🔴 **窗口正则/抽样核数据必须按【键】定位 + 留足边界** · 🔴 **"改动后读数不变"先问：探针是否消费该改动**（读数不变 ≠ 改动生效）。

## 可观测性与门禁

- 任何报告/UI 显示的数字必须能从事件流算出；算不出＝事件字典缺项，不得为某消费者单造数据。
- "不显示" ≠ "不记录"：`RngDraw`/`DrawCount` 必须记录（回放与确定性审计），仅默认不显示。
- 新增字段尾部追加+默认值；新增随机必写 `RngDraw`；预览类路径必须不掷骰。
- 同类偏差重复出现即升格为数据门禁（**P1~P27**；一句话规则 → 一条 fail-fast 校验）。

## Godot 内置工具优先（架构判定）

- **先分层再谈用不用**：内核（`core`/`sim`/`data`/`tests`）刻意零 Godot；**表现层（`ui`/`gameplay/scene`/`scenes`）必须优先用内置**（Theme / Container / Anchors / Tween / Audio / PackedScene / RichTextLabel / TileMapLayer / ShaderMaterial / Particles / `InputMap`+`Control` 焦点 / `[Export]` / `[Tool]`）。
- **五个判别问题**：①引擎是否已有该能力 ②有无内置类型/节点/资源 ③有无内置编辑器工具链让非程序员改 ④自研能否被内置替代且不破分层 ⑤必须自研（内核可测性）理由是否写注释。
- **跨层风险（实测 `O-84`）**：**同一职责不得两实现** —— 表现层读数据一律 `FileAccess`/`ResourceLoader`；`System.IO` 仅内核，且由组合根喂【字符串】；取证 `Select-String 'File\.ReadAllText|DirectoryInfo'` ⇒ `scripts/ui` 与 `scripts/gameplay/scene` **必须 0 命中**。
- **优化顺序（`#319` 调整后）**：**② Theme+容器+锚点（布局基建）优先** → ③ 焦点+手柄 → ④ 动效 → ⑤ 音效 → ⑦ 材质/字体/图标（素材路线）；🔴 **纪律：颜色/字号不得在节点上硬写**（否则"统一"是假的）。
- 🔴 **UI 验收可自动化（`#319` ⑤，记为判据）**：**所有可见 `Label` 两两不相交**（`Rect2.Intersects` 全假）· **每个 `Panel` 的 `BgColor.a == 1.0`**；⚠️ 遍历**每个界面**（战斗/城池/角色详情/地图）⇒ **"没有重叠"从"看起来还行"变成【可测】**。
- **例行审计**：每轮表现层/UI 工作复核 `godot_builtins_audit.md` §1 计数表；**优化一次挑一项**（一次一个轴）。
- **落点约定**：Theme→`resources/theme/` · 材质→`resources/shaders/` · 音频→`resources/audio/` · i18n→`resources/i18n/` · 预制件→`scenes/**/prefabs/` · 数据→`data/*.json`（表现层 `FileAccess` 读成字符串交内核解析）。
- **参考真机**（`E:\SteamLibrary\steamapps\common\DarkestDungeon`，只读）：结论见 `dd_reference_lessons.md`（六条可借鉴形态 + 三条不照抄）。
