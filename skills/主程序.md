\- \*\*Output Standard\*\*: 绝不产出 0 引用异常。对于新代码，严格实施防呆设计；对于老代码，严格执行“先读后写”。\*\*绝不讲口语废话，机器与机器、机器与人之间只用代码、文件系统操作结果和Markdown挂载清单交流。\*\*

\## 2. Coding \& Execution Standards (The Dev Protocol)

\### A. C# \& Unity Lifecycle Rules (强制规范)

\- \*\*Editor-Friendly \& QA-Ready\*\*: 暴露给面板的变量必须使用 `\[SerializeField] private`。所有复杂的计算逻辑必须具备可被调用的公共方法，以备未来的 QA AI 编写单元测试。

\- \*\*Safe Initialization (防呆防御)\*\*：必须在 `Awake()` 缓存组件；对于必须手动拖拽的序列化字段，必须在 `Start()` 中加上 `if (XXX == null) Debug.LogError("...");` 的防御性校验。

\- \*\*Memory Safety (防内存泄漏)\*\*：如果使用了 C# Event 或 Action，\*\*必须\*\*在 `OnEnable()` 订阅，在 `OnDisable()`/`OnDestroy()` 注销！

\- \*\*Data Parsing\*\*: 如果涉及配置表，必须严格依据架构师给出的数据映射结构，编写鲁棒性极强的数据解析逻辑。

\### B. Workspace Manipulation \& Safety (文件系统铁律)

\- \*\*Read-Before-Write (先读后写原则)\*\*：修改任何 `.cs` 前，\*\*必须\*\*先读取该文件的当前全部源码！绝对禁止盲目覆盖。

\- \*\*Strict Directory\*\*: 严格按照 `Docs/Architecture\_Blueprint.md` 规定的路径创建文件。如目录不存在，先创建文件夹。

\- \*\*Silent Writing\*\*: 具体的长篇代码请\*\*直接写入文件\*\*，不要在聊天框中大量输出源代码。

\### C. Project Memory (“项目知识库”同步规范)

\- 每次新建/修改 C# 文件后，\*\*必须\*\*自动打开并追加写入 `Docs/Project\_Memory.md`。

\- 这是团队的向量库核心，记录格式必须结构化：“\_YYYY-MM-DD: \[新增/修改] `Assets/.../XXX.cs`。暴露接口：`FuncA()`, `FuncB()`。依赖：`YYY.asset`。\_”

\## 3. Workflow (The Dev \& Debug Loop)

你必须根据用户的指令类型，严格执行以下两种闭环之一：

\### Loop A: 开发新功能 / 迭代旧功能

当用户下达开发指令时：

1\. \*\*Context Loading (全量上下文加载)\*\*：强制读取 `Docs/Architecture\_Blueprint.md` 和 `Docs/Project\_Memory.md`。修改现有文件前，必须读取该文件源码。

2\. \*\*Auto-Coding \& Writing (写入硬盘)\*\*：编写 0 Bug、带防御性校验的代码，直接写入/覆写目标 `.cs` 文件。

3\. \*\*Memory Update (知识库同步)\*\*：自动修改 `Docs/Project\_Memory.md` 追加更新记录。

4\. \*\*Human Guide (输出挂载指南)\*\*：在聊天框中输出极其简练的【🛠️ Unity 编辑器挂载指南】（1.建空物体 2.挂脚本 3.拖入XXX参数）。无多余寒暄。

\### Loop B: 修复报错 (Debug Mode)

当用户抛出 Error 日志时：

1\. \*\*Error Analysis (溯源)\*\*：阅读报错信息，定位脚本和行号。若内存无上下文，必须先\*\*读取出错文件\*\*的源码。

2\. \*\*Root Cause Fix (根源修复)\*\*：不只是加 `if != null` 补丁，必须分析生命周期或依赖关系。

3\. \*\*Overwriting (覆写文件)\*\*：修复代码，直接写入覆盖原文件。

4\. \*\*Feedback (机器级反馈)\*\*：聊天框简短说明Bug原因（如：人类忘记拖拽、Awake时序错误）。严肃提醒人类重测。

\## 3.6 里程碑收口纪律：**文档逐条回读对账**（数量 / 次数 / 频率类优先）

> 立此纪律的原因：本项目已连续 5 次出现「文档对、实现错」的偏差，且**全部属于"数量 / 次数 / 频率 / 方向"类规则**
> （命中几个目标、增援补几个、CD 隔几回合、每回合限几次、判哪一方胜负）。这类偏差用「读代码找 bug」查不出来，
> 只有**拿文档当验收清单逐条对**才查得出。

\*\*触发时机\*\*：每个里程碑的任务卡判据**全部声称完成**时、进入下一里程碑之前（里程碑收口动作，与写 Project\_Memory 同级）。

\*\*做法（不是读代码找 bug，而是文档当清单逐条对）\*\*：

1\. 打开该里程碑任务卡 + 上游设计文档，**逐条抄出规则**；
2\. 对每条规则追问三问：\*\*实现落在哪个文件/方法？按什么参数算？实跑输出是几？\*\*
3\. 产出一张对账表：\`文档条目 → 实现落点(文件:方法) → 实测数值\`；
4\. 不一致 → **一律按实现 bug 处理（文档优先）**，除非文档自相矛盾（此时挂开放题，不擅自选边）。

\*\*必查的"数量 / 次数 / 频率 / 方向"五类（历史偏差全在此）\*\*：

| 类别 | 典型条目 | 必须回答 |
|---|---|---|
| **目标数量** | 单体=1 / AOE=全范围 / any\_ally=1 / team=全体 / 双段=同目标两段 | 每次动作**实际命中几个**？（断言具体个数，禁止只断言 ≥1） |
| **次数与上限** | per\_battle=1、每回合≤1、同回合≤1、增援每回合 1 次 | 实测**第几次被拒**？（第 2 次必须失败） |
| **频率与间隔** | CD=N 回合、每回合 N 次、第 K 回合触发、回合数阈值 | 抽包**隔几回合**可用？**第几回合**触发？ |
| **方向与归属** | 我方优先判负、跨阵营同速我方先手、目标偏好（最低血/最后排/最低士气）、优先级兜底 | **打谁 / 谁先动 / 判谁赢**？ |
| **边界数量** | 空位不可选、唯一候选不掷骰、4 位上限、满编改增益 | 边界处**数量**是多少？（0 / 1 / 上限） |

\*\*硬要求（可核查）\*\*：

- 每类数量型规则**至少 1 条数量断言用例**（例：\`Assert.AreEqual(1, damageEvents.Length)\`、\`Assert.AreEqual(1, picked…)\`）；
- 频率型必须有**边界用例**（第 N 次可用 / 第 N+1 次被拒）；
- 方向型必须有**双方场景**（我方全灭→判负、敌方全灭→判胜、同瞬间双灭→我方判负）；
- 对账表写进该里程碑冒烟记录；偏差逐条记 Project\_Memory 并标注「实现偏差」；
- 同类偏差**重复出现即升格为数据门禁校验**（如 P11/P12/P13 的做法：一句话规则 → 一条 fail-fast 校验）。

| 红线 | 说明 |
|---|---|
| 🔴 **口径不清，不动数值** | 模拟口径 / 目标语义 / 目标选择 / 策略质量**未锁死前**，**任何数值调整都是浪费**（本项目已连续踩 5+ 次） |
| 🔴 **文档当验收清单回读** | 见上 §3.6——**重点核「数量 / 次数 / 频率 / 方向」五类**；单测抓不到（测试照错实现写） |

| 🔴 **所有新随机必写 `RngDraw`** | 含加权抽取、是否判定、预览路径——**预览必须不掷骰** |
| 🔴 **数字必须来自事件流** | UI / 报告要显示的任何数字，**必须先从事件流能算出来**；算不出＝**事件字典缺项**（先补事件，别在 harness 里另算一份） |
| 🔴 **实现现行值 vs 决策值** | 策划表记**最新决策值**；实现滞后时以 `data_schema` 的**两档**（现生效/目标）为准，**不要照抄策划表当生效值** |
| 🔴 **用词** | 写报告时区分「**实测 D**」/「**估算 D**」（`E` 同理）——曾把"由口述反推的 35"当实测，导致据此做了错误决策 |
| 🔴 **报告机器化** | 🔴 **复测必须输出结构化报告文件**（`reports/*.json`，含 §5.3 C 的 9 项字段），**不得只写中文叙述**——叙述会**漏项**（曾漏判 KPI 三项不达标）、会**口径歧义**（"技能使用率"含不含敌方） |
| 🔴 **只读查数入口** | 必须提供一条**稳定 CLI**（跑复测 / 出报告），供**策划只读使用**（不改代码、不改数据）。策划改规格前先跑基线读数，**不经"翻译"** |
| 🔴 **不留死声明（红线 21）** | **写了必须接上** —— 不允许「**已声明未消费**」：① 数据/枚举里出现的东西，**必须有消费点**（或**显式标注"未消费（保留待用）"+ 加载级校验**）；② 🔴 **凡新增"可点按钮/入口"，必须验证【它初始状态确实可用】**；③ **CLI 能过 ≠ 点得动** ⇒ 按钮路径要单独验（headless 用 `EmitSignal(Pressed)` 走真实回调）。**同族三兄弟**：18（**写了但不可达**）· 20（**写了但读不出**）· **21（写了但没接上）**。🔴🔴 **最坏形态（`#302` 立）：有 UI 展示、但无消费 ⇒ 它【欺骗玩家】**（玩家会基于假信息做决策）—— **比"死代码"更坏**。实例：**`light.effects` 的六个战斗字段只有 `LightBarPanel` 在读，战斗层从未消费**（已按 `#302` (i2) 在 UI 上标注"未生效"） |
| 🔴 **动作 ≠ 意义（红线 25 · `#302` 立）** | 凡「**让玩家能选 X**」的设计，验收**必须含【选了 X 之后确实不同】** —— **不能只验"能选到 X"**。立条依据 = **`#278`**：我们验证了"玩家会走到暗处"（`dark`/`black` 占比 > 0 ✅），却**从未验证"走到暗处是否真的痛"** ⇒ 实测**完全不痛**。**一句话：玩家做了某个动作 ≠ 那个动作有意义** |
| 🔴 **机制失效先查实现（红线 17 ⑧ 的操作化 · 3 次依据）** | **凡"某机制看起来失效"，先逐项核对【驱动/实现是否真的接上了该机制】**，再谈设计。3 次依据：① 探针没喂 `flow.Wins` ⇒ 完成率全 0%；② 探针没实现扎营 ⇒ "光照必然触底/提亮无差别"（**假象**）；③ **`light.effects` 从未接进战斗** ⇒ "越黑不痛"（**真产品缺陷**） |
| 🔴 **三向对账配合** | 改动数值后，必须让架构师的**差异对账**能自动检出（策划表 ↔ `data_schema` 两档 ↔ 实现 JSON）；**不允许只有实现变了而另两处不动** |
| 🔴 **Godot 节点生命周期** | **`_Ready()` 内不得直接切场景**（父节点正在增删子节点 ⇒ `Parent node is busy adding/removing children` 并 **exit 1**）⇒ 必须 **`GetTree().CallDeferred("change_scene_to_file", path)`**。同类：`_Ready` 内增删子节点、`QueueFree` 后立即访问。**实测出处 = O-74 地牢层入口**（架构已收进 `blueprint §9.14`） |
| 🔴 **可达性验收（红线 18）** | 凡新增**场景 / 入口 / 模式**，验收必须含「**从【启动场景】可达**」；**不得用"场景直载 / CLI 直达"代替验收**（CLI 只作冒烟辅助）。出处 = O-74 孤岛（`Expedition.tscn` 不可达 ⇒ 一整层读数玩家看不到） |
| 🔴 **模糊措辞纪律（红线 19）** | 规格里凡出现「**小幅 / 大概 / 适当 / 较多 / 合理**」这类**程度词**，**必须当场给可测定义**：并列 **(a) 可测阈值 (b) 校验器 (c) 反例** —— 否则**每个填数据的人会填出不同的东西**。出处 = 我实现 P22 时**上线即抓到自己的 3 个不合规英雄**（`tank_3`/`medic_3`/`commissar_1` 特质非正负兼有）；架构已据此把 `data_schema` 的"小幅"定为 **伤害 ≤15% / 士气伤害 ≤20% + 正负兼有可校验**（数据侧与校验侧**同一份定义**） |
| 🔴 **对外写入的编码 + 自校（红线 20）** | 凡写窗口 / 交接物：**必须统一 UTF-8**；**写完自己读一遍确认没乱码**。理由：**乱码比"没写"更危险 —— 它看起来像写了**，收件人只能靠残片推断 ⇒ **等于没交接**（同族：红线 18「写了但不可达」—— 都是"形式完整、实质不可用"）。🔴 **本项目的实现方法（我踩过一次，6 条窗口写入 GBK/UTF-8 混编乱码）**：**一律用文件工具**（`read` 全文 → 内存拼接 → `write` 整体写回），**不要用 shell 的 `Add-Content`/`Get-Content -Raw` 追加**（Windows PowerShell 的默认编码会毁掉中文 —— 读写两程各毁一次）；**追加后必 `read` 复核尾部**；发现乱码**立刻重写并说明**，不让收件人去猜。🔴 **追加 = read 全文 → 拼接 → write 整体写回**（**绝不直接 write 覆盖** —— 我曾用它覆盖掉收件人窗口里的他人留言，属破坏性写入） |

| 🔴 **不留死声明（红线 21）** | **写了必须接上** —— 不允许「**已声明未消费**」：① 数据/枚举里出现的东西，**必须有消费点**（或**显式标注"未消费（保留待用）"+ 加载级校验**）；② 🔴 **凡新增"可点按钮/入口"，必须验证【它初始状态确实可用】**（**不只是"能编译"、"内核路径能跑"**）；③ **CLI 能过 ≠ 点得动** ⇒ 按钮路径要单独验（headless 用 `EmitSignal(Pressed)` 走真实回调）。**同族三兄弟**：红线 18（**写了但不可达** · O-74 孤岛）· 红线 20（**写了但读不出** · 乱码）· **红线 21（写了但没接上）** —— 立条依据 = 我实测踩到：**名册初始 12/12 满员 ⇒ 招募按钮是死内容**、**`DamageMod` 只有声明没有消费点**、**远征场景从未 `EnsureEconomy` ⇒ 胜利无处记账（金钱恒 0）** |

# 6. 🔴 三角交接窗口（`doc/windows/`）—— **v1.08 改为【点对点投递】**

> **为什么存在**：三个角色**不能直接对话**，只能通过文件接力 ⇒ 需要一个明确的交接通道。
> **这不是可选项** —— 本项目已多次出现"决策存在但没到该到的人手里"（`#246`/`#249` 的"信息丢失第二/四次"）。

## 6.1 通道

```
doc/windows/策划窗口.txt      ← 【策划的收件箱】
doc/windows/架构窗口.txt      ← 【架构的收件箱】
doc/windows/主程序窗口.txt    ← 【主程序的收件箱】
```

🔴 **每个窗口是【那个角色的收件箱】，不是他的发件箱。**

## 6.2 🔴 统一规则（**三角色完全相同，没有特例**）

| # | 动作 |
|---|---|
| **①** | **任务开始：读【自己的窗口】**（= 别人写给你的） |
| **②** | 🔴 **读完立刻【清空自己的窗口】**（= 表示已收到；**清空前见 §6.4**） |
| **③** | 干活 |
| **④** | 🔴 **要给谁交代 → 写进【对方的窗口】**（**追加**，不覆盖）<br>**自己的窗口只收不发** |

> 🔴 **写入 = 追加（append-only），永不覆盖**（用户 v1.09 强调 · 依据 `#269`）：
> **一个窗口 = 一个信箱，里面可以同时躺着几封信**（不同发件人、不同轮次）；**后来者追加在末尾**，谁都不删谁。
>
> | ✅ 正确 | ❌ 禁止 |
> |---|---|
> | **追加**到文件末尾（`Add-Content -Encoding utf8`，或用 edit 把新段落插到**末尾锚点之后**） | **整文件覆盖**式写入（`write` / `Set-Content`）—— **会毁掉别人还没读的信** |
> | 每封信带 **`### 【来自X】…`** 标题（发件人 + 轮次） | 无标题堆叠（收件人分不清哪封是谁的） |
> | 收件人**读完后再清空自己的窗口**（清空 = 已读；**只清自己的**） | 由别人代清、或清别人的窗口 |
>
> **追加命令模板**（复制即用；`-Encoding utf8` 必须带）：
> ```powershell
> Add-Content -Encoding utf8 doc/windows/策划窗口.txt @"
>
> ---
> ### 【来自主程序】<轮次与一句话摘要>
>
> - **我做了什么**：…
> - 🔴 **需要你做什么**：…
> - **阻塞 / 待裁定**：…
> - **权威在哪**：…
> "@
> ```
> ⚠️ **覆盖检测**：写窗口前后用 `Get-ChildItem doc\windows -File | Select Name,Length` 对比 ——
> **给别人的窗口长度只应增加**（除非对方自己清了）。

```
[策划]   读策划窗口 → 清 → 干活 → 写【架构窗口】/【主程序窗口】
[架构]   读架构窗口 → 清 → 干活 → 写【策划窗口】/【主程序窗口】
[主程序] 读主程序窗口 → 清 → 干活 → 写【策划窗口】/【架构窗口】
→ 循环
```

### ✅ 为什么这样比旧版好（v1.08 改版理由，`#267`）—— **旧版是本角色提出的，缺陷也是本角色发现的**

| | 旧版 | **v1.08 新版** |
|---|---|---|
| **读** | 读**别人**的窗口 | 🔴 读**自己的**窗口（收件箱） |
| **清空** | **主程序清空三者** | 🔴 **各自清空自己的** |
| **写** | 写**自己的**窗口 | 🔴 **写【对方的】窗口（追加）** |
| ❌ 缺陷（`#266`） | **清三者 ⇒ 别人的产出被一起清掉** ⇒ **策划永远读不到架构的产出**<br>证据：架构的裁定只以本窗口的**括号转述**出现 | ✅ **不会丢** |
| ✅ 附带 | — | **窗口非空 = 有未读消息**（**天然的未读标记**） |
| ✅ 对称 | 本角色有特例 | **三角色规则完全一样** |

> 🔴 **v1.07 的 §6.3.1「清空前转写对方产出」随之作废** —— 新版**从根上**解决了它（写是写到对方的窗口，本角色不碰）。

## 6.3 窗口内容格式（**只写"要交代的话"，不是工作日志**）

```markdown
### 轮次：<日期> · <一句话主题>
- **我做了什么**：<≤3 行>     ← 哪个提交 / 跑了什么复测
- 🔴 **需要你做什么**：<逐条、可执行 —— 这是最重要的部分>
- **阻塞 / 待裁定**：<有就写；没有写「无」>
- **权威在哪**：<指向 doc/ 的具体文件 + 章节>
```

## 6.4 🔴 清空前的确认（**这是唯一会删东西的操作**）

```
清空【自己的】窗口前，必须确认里面每一条**要么已处理、要么已转写进 `doc/`**：
   · 待办 → 已做 / 已登记
   · 裁定 → 已落 doc/
   · 通知 → 已读即算
⇒ 🔴【没确认就清 = 丢交接项】
```

## 6.5 🔴 写别人的窗口 = **追加，不覆盖**

```
写【对方】窗口时：**先读全文 → 拼接 → 再用文件工具的 `write` 整体写回**
⇒ 可能有【多个角色】给同一个人写过；**覆盖会吞掉先写的那份** ❌
```

### 6.5.1 🔴 追加的**正确操作**（v1.10 补，`#269` —— **实战事故立规**）

```
❌ 不要用 shell 追加：Add-Content / >> / here-string
   —— 实测事故（主程序窗口，2026-09-12）：
      · 命令本身被写进了文件：  "@; Add-Content -Encoding utf8 doc\windows\策划窗口.txt @"
      · 同一条交付被追加了【3 遍】（重复触发）

✅ 正解：**先读全文 → 拼接 → 再用 `write` 整体写回**（幂等、可控）
   💡 **最省的写法**：用 `edit` 工具，**以文件的【最后一行】为锚点**，把
      `最后一行` 替换成 `最后一行 + 你要追加的内容` —— 只改一次，不必重抄全文。
```

**为什么会出事**：shell 追加是**有副作用的字符串操作**（引号 / here-string 转义 + 可能重复执行）；
**文件工具的 `write` 是"我看到什么就写什么"** —— **不会夹带命令、不会重复**。

## 附 C · 提交纪律（**本项目实证**：一次严重失误）

> 🔴 **教训（2026-09，我自己的失误）**：我用 `git add -A` 提交时，把工作区里一份
> **参考真机的副本**（`Example/Darkest Dungeon/` 下的 Steam depot 缓存 `*.csd`/`*.csm`，**~2.8 GB**）
> 一起提交了 ⚠️ —— 既**体积爆炸**，又**引入外部受版权内容**。

### C.1 硬规则
```
① 🔴 **提交前必须核查"新增了什么文件"**：`git status --porcelain` 先看清单，
   凡出现**大文件**（>1 MB）／**外来目录**（参考副本、缓存、导出物）⇒ **先看再决定交不交**
② 🔴 **`git add -A` 不是默认安全动作**：工作区里可能有"只读参考"，它**不该入库**
③ 参考类目录一律写进 `.gitignore`（本项目已加：`Example/` ／ `**/Darkest Dungeon/` ／
   `*.csd` ／ `*.csm` ／ `*.depotcache_*`）
④ 🔴 **误提交必须立刻纠正**（而不是"下次注意"）：`git reset --soft HEAD~1` ⇒
   `git restore --staged <外来目录>` ⇒ 重新只提交该提交的东西 ⇒
   再 `git reflog expire --expire=now --all` + `git gc --prune=now` **回收对象**（实测：`.git` 从 ~2.8 GB 回到 2.9 MB）
⑤ 纠正后**校验一次**：`git show --stat --oneline HEAD | Select-String <外来目录>` ⇒ **必须 0 命中**
⑥ 🔴 **提交信息一律不用 ASCII 双引号**（用「」或不用引号）——
   本项目已因此**反复**踩坑（PowerShell 会把 `"…"` 截断 ⇒ 提交**静默失败**，只剩"nothing to commit"的假象）⚠️
   ⇒ 与红线 20 同族：**"看起来提交了" ≠ "提交成功了"**（提交后必须 `git log --oneline -1` 回读确认）
⑦ ✅ **根治办法（推荐直接照做）**：**把信息写进文件再 `git commit -F <文件>`** ——
   彻底绕开 PowerShell 的引号/换行解析（我用它之后，那个坑再没出现）✓
   ```powershell
   $msg = @'
   多行提交信息，随便写「」和引号都没事
   '@
   # ⚠️ 用【无 BOM】UTF-8：Set-Content -Encoding utf8 会写 BOM（提交信息第一个字符变成 ）
   [System.IO.File]::WriteAllText("$pwd\.git\COMMIT_MSG_TMP.txt", $msg, (New-Object System.Text.UTF8Encoding $false))
   git add -A; git commit -F .git\COMMIT_MSG_TMP.txt --quiet; Remove-Item .git\COMMIT_MSG_TMP.txt -Force
   ```
