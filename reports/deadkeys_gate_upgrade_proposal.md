# 门禁判据升级**方案**：`--deadkeys` 的"映射键"误判（主程序提出 · **未实施**）

> 🔴 **为什么只出方案不动手**：改门禁本体 = 改**判据**，属于"工具/架构口径" ✓
>   而我手上只剩几轮 ⇒ **不在末段引入判据级风险** ✓（我**已把 15 条按现机制如实登记**，门禁现为 0 处 ✓）

## 1. 问题（实测）
```
`hero_upgrades.json` 的 **15 个 hero id** 被判"死数据" ✗ —— 实测复现：
   `[deadkeys] … hero_upgrades.json: 键 "crusader" 在任何 .cs 里都不出现 ⇒ 疑似死数据`
🔴 但它们是**映射键**：`heroes.<id>.trees[…]` ✓ 由 `HeroUpgradesConfig` **按字典泛读** ✓
   （`[property: JsonPropertyName("heroes")] IReadOnlyDictionary<string, HeroUpgradeClassConfig> Heroes` ✓）
⇒ 📌 扫描器的判据是「**字面量 grep `.cs`**」⇒ 对**泛读的键**天然不适用 ✓
   ⇒ 这不是"我们漏接线" ✗，而是**判据的适用边界** ✓
```

## 2. 提议的规则（**保守**：只放过"能证明被泛读"的键）
```
对某个数据文件 F：
  ① 取 F 的**顶层容器键** C（例：`hero_upgrades.json` ⇒ `heroes` ✓；
     若 F 的根是数组/多容器，则对每个顶层键各判一次 ✓）
  ② 在 `darkest/scripts/**` 里找**声明了该容器**的代码：同时满足
       (a) 有 `JsonPropertyName("C")`（或属性名 == C，大小写不敏感 ✓）
       (b) 其类型是**字典/集合**（`IReadOnlyDictionary<` / `Dictionary<` / `IReadOnlyList<` ✓）
  ③ 满足 ⇒ 该容器下的**子键**一律**不报**"死数据"（因为它们由泛读消费 ✓）
       ⚠️ **但容器本身若无人读 ⇒ 仍报**（这一条不能松 ✗）
  ④ 不满足 ⇒ **行为与今天完全一致**（一条都不放过 ✓）
```
## 3. **双向自检**（与 `check_data_discipline.py --selfcheck` 同款纪律 ✓）
```
正向：注入一个**无人泛读**的容器 + 一个子键 ⇒ **必须仍被报出** ✓（判据没被放宽成"都不报"）
反向：注入一个**有泛读**的容器 + 一个子键 ⇒ **必须不报** ✓（新规则真的生效）
⇒ 两条都过才算改对 ✓ —— 否则这个升级就是"把红改绿"的化妆 ✗（那正是本纪律禁止的）
```
## 4. 影响面（先说清）
```
· 现读数：`三扫合计可疑 0 处`（**靠 15 行白名单**换来的 ✓ 每条都写了"扫描器不适用"的理由 ✓）
· 升级后：那 **15 行白名单可以删掉**（判据自己认得泛读 ✓）⇒ 白名单更短、更可审 ✓
· ⚠️ 风险：规则若写松（例如"该文件里出现过 `Dictionary` 就放过全部键"）⇒ **会藏住真死数据** ✗
   ⇒ 所以 §2 的 (a)+(b) 必须**同时**满足，且**只针对顶层容器键** ✓
```
